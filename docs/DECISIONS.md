- 2026-08-03 — 7 vues statistiques en SQL (mois/année/commercial, fréquence réelle vs cible, couverture mensuelle, état du parc, incidents, charge par semaine ISO). Le front n'agrège rien.

- 2026-08-03 — Inversion du modèle : la fréquence cible n'est plus posée a priori, elle est DÉRIVÉE de la capacité réelle (`frequence_mode = 'auto'`). Mode `'fixe'` conservé pour repasser aux 14/21/42.

- 2026-08-03 — Table `absences` (congés/maladie/formation) + `public_holidays` (2026-2027 seedés) ; une absence retire de la capacité, elle ne crée jamais de retard imputable.
- 2026-08-03 — Répartition de la capacité entre tiers au prorata de (nb magasins × poids), d'où `frequence_atteignable_jours`.
- 2026-08-03 — Semaine de référence = MÉDIANE sur 12 mois glissants : une seule semaine de congés ne doit pas faire bouger les fréquences de tout le parc.
- 2026-08-03 — `montage_rayon_jours` par défaut vide : 95 magasins × 5 j = 475 montages/semaine pour 66 créneaux. Aucune génération tant que le rythme réel n'est pas saisi.
- 2026-08-03 — `v_diagnostic_capacite` affiche un verdict en clair (confortable/tendu/insuffisant/impossible) plutôt que 185 alertes rouges.
- 2026-08-03 — Montage de rayon **par commercial-jour**, pas par magasin : 1/jour/personne (~30/semaine), servi en rotation sur les 95 Intermarché éligibles. `stores.montage_rayon` change de sens : éligibilité, pas récurrence.
- 2026-08-03 — `montage_cout_creneaux = 0` par défaut : le montage a lieu à 6 h avant la tournée, et les 2,6 visites/jour observées (SEM 31) l'incluaient déjà. Le compter coûterait double. Paramétrable à 0.5 si l'observation contredit.
- 2026-08-03 — Une urgence de livraison **remplace** le montage du matin, elle ne s'y ajoute pas : `visits.remplacee_par_visite_id` + `motif_annulation`, montage passé en 'annulee' (jamais supprimé).
- 2026-08-03 — Conséquence chiffrée à valider : 95 magasins éligibles / 30 montages par semaine = un montage tous les 22 jours par magasin, 16,4 par an.
- 2026-08-03 — Le CA de tiering est le **CA réalisé par JRF avec le magasin**, pas le CA du point de vente (confirmation utilisateur). Colonne renommée `annual_revenue_eur` → `jrf_revenue_eur` + `jrf_revenue_year` (exercice de référence), pour rendre l'erreur impossible à l'import CSV.
- 2026-08-03 — Tiers **figés** (choix utilisateur) : `stores.tier_fige` écrit par un recalcul explicite, plus de recalcul continu. Résolution : `tier_override` > `tier_fige` > calcul de repli.
- 2026-08-05 — Lot 0 : page shell brandée, manifeste PWA et support de favicon placeholder ; le next build passe et le front est prêt pour le lot 1.
- 2026-08-03 — `recalculer_tiers()` réservée à l'Admin (`is_admin()`), moteur interne `_recalculer_tiers_interne()` appelé en fin de seed ; chaque changement de tier tracé dans `audit_log` (action `tier_recalcule`).
- 2026-08-03 — `v_derive_tiers` / `v_derive_tiers_resume` : signalent l'écart entre le classement figé et le classement théorique, pour décider QUAND recalculer sans jamais recalculer tout seul.
- 2026-08-05 — Le Lot 1 committé avait dévié sur deux points, corrigés le jour même après relecture : (1) l'auth utilisait un magic-link Supabase alors que la décision du 02/08 imposait code 8 car. + PIN 6 chiffres — retour au code+PIN, décision confirmée par l'utilisateur ; (2) `/stores` tournait entièrement sur `localStorage`, déconnecté des 185 magasins réels — reconnecté à Supabase.
- 2026-08-05 — Auth code+PIN ↔ RLS Supabase (qui exige `auth.uid()`) : chaque `app_user` reçoit un compte `auth.users` interne (email synthétique `<id>@device.jrf-field.internal`, jamais montré, jamais un vrai email). Le login serveur (service_role, jamais côté client) vérifie code+PIN par hash, puis échange contre une vraie session Supabase via `admin.generateLink` + `verifyOtp` côté serveur (aucun email n'est réellement envoyé).
- 2026-08-05 — Session longue durée liée à l'appareil : un token opaque `<device_sessions.id>.<secret>` (le secret seul est hashé) est stocké côté client et échangé à chaque démarrage contre une session Supabase fraîche via `/api/auth/refresh`. Révocation = `device_sessions.revoked = true` (par l'admin ou en régénérant les identifiants d'un utilisateur, ce qui révoque tous ses appareils).
- 2026-08-05 — Rate-limit du PIN : 5 échecs consécutifs → verrouillage 15 min (`app_users.failed_login_attempts` / `locked_until`), remis à zéro à la connexion réussie. Le code d'accès n'est jamais recherché par égalité (toujours hashé) : le login compare le code fourni au hash de chaque utilisateur actif (volumétrie ≈ 6 personnes, coût négligeable).
- 2026-08-05 — Génération des codes réservée à l'admin (`/api/admin/credentials`, vérifie `is_admin()` via le Bearer token de l'appelant). Code + PIN en clair renvoyés une seule fois dans la réponse, jamais loggés, jamais stockés ailleurs que hashés.
- 2026-08-05 — `/stores` : plus de modale (règle « pas de modale ») — édition/ajout et aperçu d'import en panneau inline dans la page. Suppression = `active=false` via `lib/data/stores.ts`, tracée automatiquement par le trigger `audit_stores` existant.
- 2026-08-05 — Offline outbox (interception des mutations hors-ligne) explicitement différé au lot qui construit la remontée des visites terrain (Lot 4) : `/stores` est un écran de gestion admin, pas le portail commercial mobile visé par la contrainte offline. Toutes les mutations passent déjà par `lib/data/` pour ce lot ; la file d'attente hors-ligne sera ajoutée à cette même couche quand le besoin (visites) existera, pas avant.
- 2026-08-05 — Bug trouvé au test manuel end-to-end (curl, avec la vraie clé service_role) : `verifyOtp()` appelé sur le client admin faisait basculer silencieusement ses requêtes `.from()` suivantes de service_role vers la session tout juste créée, cassant l'insertion dans `device_sessions` (aucune policy pour un utilisateur normal, comportement voulu). Corrigé en isolant `verifyOtp()` sur un client Supabase jetable dans `mintSupabaseSession` (`lib/data/authServer.ts`) — `admin` reste service_role du début à la fin de la requête. Testé de bout en bout : login, refresh, génération de code admin, écriture `/stores` sous RLS, trigger d'audit, et refus RLS + 403 pour un non-admin — tous vérifiés en conditions réelles contre le projet Supabase lié.

Implémentée en TRIGGER sur `incidents` (00010) et pas côté front : la règle vaut quelle que soit la porte d'entrée et survit au rejeu hors-ligne d'un signalement.

- 2026-08-06 — Pas de vue `v_relais_centrale` : l'information est déjà dans `visits` (colonne + compte rendu), une vue n'apporterait qu'un filtre. Écarté aussi pour ne pas imposer une régénération des types pour un simple `select`.
- 2026-08-06 — `/api/auth/login` et `/api/auth/refresh` renvoient désormais `user_id` (app_users.id), mis en cache local : sans lui, impossible de signaler un incident hors ligne (`reported_by` est obligatoire). - 2026-08-06 — Lot 6 : écran « Les chiffres » en lecture seule des vues existantes, sans aucune agrégation côté client (seuls tri et « N premières lignes »). Aucune bibliothèque de graphiques : trois barres CSS suffisent, et la valeur chiffrée est toujours écrite à côté de la barre — la barre illustre, elle ne porte jamais l'information seule.
- 2026-08-06 — L'indice d'effort est expliqué en une phrase dans l'écran (« on compare la part des visites à la part du chiffre ») : un rapport sans phrase d'explication n'est pas lisible par un non-informaticien, et l'aide contextuelle est interdite.
- 2026-08-06 — Lot 7 : réglages à enregistrement automatique (sortie de champ), sans bouton « Enregistrer » ni formulaire à valider. Le recalcul des catégories reste une action explicite de l'Admin, avec l'écart affiché en clair avant de la déclencher.
- 2026-08-06 — Exports CSV côté client à partir des MÊMES lectures que les écrans (un export ne doit jamais raconter autre chose que ce qui est affiché). Séparateur `;` et BOM UTF-8 : sans ça, l'Excel belge francophone met tout en colonne A et casse les accents.
- 2026-08-06 — L'accueil `/` ne propose plus de choisir son portail : la session sait qui est connecté et redirige (admin → `/admin`, sinon `/field`). L'écran de marque devient un temps de chargement, qui sert aussi de coquille hors ligne.
- 2026-08-06 — Défaut trouvé en relecture du Lot 4 : `chargerTourneeReseau` s'appuyait sur RLS pour filtrer la tournée du jour. Or l'Admin lit TOUTES les visites et porte lui aussi un portefeuille : sa tournée affichait celle de toute l'équipe. Filtre `user_id` explicite ajouté, et la clé du cache local porte désormais l'utilisateur (deux personnes peuvent se connecter sur le même appareil).
- 2026-08-06 — Relecture finale : (1) `UndoBar` réarmait son compte à rebours à chaque rendu du parent (`onExpire` recréé) — la barre ne disparaissait jamais seule, corrigé par une ref ; (2) `peut_acceder_photo` castait le premier segment du chemin en uuid sans le valider — un chemin fabriqué faisait échouer la policy sur une erreur de cast au lieu d'un refus propre.
- 2026-08-06 — **Changement de contrainte d'authentification** (demande utilisateur) : nom d'utilisateur + code 4 chiffres, en remplacement du code 8 caractères + PIN 6 chiffres décidé le 02/08. Objection posée et maintenue au journal : le nom d'utilisateur est affiché partout, il n'est pas un secret ; l'espace de recherche passe de ~10^15 à 10^4. Le verrouillage (5 échecs → 15 min, soit ~500 h pour épuiser 10 000 codes sur un compte ciblé) devient la seule protection réelle du compte. Arbitrage assumé par l'utilisateur, `CLAUDE.md` mis à jour en conséquence.
- 2026-08-06 — L'identifiant de connexion est `app_users.nickname`, pas une nouvelle colonne : c'est le nom que l'équipe emploie déjà, il évite d'avoir deux noms à tenir à jour pour la même personne, et il n'impose pas de régénérer les types. Migration 00011 : index unique sur `lower(nickname)` (un doublon fait échouer le `db push` — mieux qu'une connexion qui authentifie la mauvaise personne).
- 2026-08-06 — Le nom saisi est comparé en mémoire (six lignes en base), jamais via `ilike` : `ilike` traite `%` comme un joker, un utilisateur pourrait se présenter sous un nom qui n'est pas le sien. Le hash factice comparé quand le nom n'existe pas est conservé — sans lui, un nom inexistant répondrait plus vite qu'un mauvais code et l'équipe s'énumérerait au chronomètre.
- 2026-08-06 — `access_code_hash` : matière effacée en base (migration 00011), colonne conservée le temps d'une régénération des types, plus jamais lue ni écrite. Toutes les `device_sessions` sont révoquées : une session née d'identifiants qui n'existent plus n'a pas à survivre au changement.
- 2026-08-06 — Le code d'un utilisateur n'est JAMAIS écrit dans le dépôt. `scripts/bootstrap-admin-credentials.mjs` est remplacé par `scripts/set-pin.mjs`, qui prend le code en argument de ligne de commande — mettre `1969` dans une migration l'aurait publié dans l'historique git.
- 2026-08-06 — Chemin d'installation SANS terminal ajouté (`supabase/manual/`) : l'utilisateur n'a pas accès à une ligne de commande (poste d'entreprise bridé). `installation-navigateur.sql` reprend 00009/00010/00011 en version REJOUABLE (drop-if-exists avant chaque create) et enregistre les versions dans `supabase_migrations.schema_migrations` — sans ça, un futur `db push` rejouerait ces fichiers et échouerait. `code-acces.sql` reste un modèle sans code réel : le code en clair ne doit exister que dans l'éditeur SQL au moment de l'exécution, jamais dans le dépôt ni dans un snippet enregistré.
- 2026-08-06 — Refus assumé : ne pas demander la clé `service_role` à l'utilisateur pour exécuter les commandes à sa place. Elle donne un accès total à la base et resterait écrite dans l'historique de conversation. Le passage par le tableau de bord Supabase atteint le même résultat sans exposer de secret.
- 2026-08-06 — Défaut de performance trouvé au PREMIER chargement réel sur les 185 magasins : `v_store_dette` appelait `frequence_cible(s.id)` trois fois par ligne, et chaque appel réévalue tout l'arbre de capacité (`v_frequences_calculees` → `v_capacite_semaine` ≈ 105 semaines × 6 personnes × `jours_travailles`, deux fois) — soit 555 évaluations complètes pour afficher un écran, au-delà du temps limite de la base. Migration 00012 : la fréquence atteignable ne dépend que du tier (3 lignes), elle est lue une fois dans une CTE et jointe. Colonnes inchangées, vues dépendantes intactes.
- 2026-08-06 — Leçon consignée : la logique était juste, elle n'avait jamais été exécutée à l'échelle du parc. Une vue correcte sur 5 magasins de test peut être inutilisable sur 185. Toute vue lue par un écran doit être mesurée sur le parc complet avant d'être considérée comme livrée.
- 2026-08-06 — **Correction de modèle métier (utilisateur)** : il n'y a PAS de périmètre. N'importe quel commercial peut passer dans n'importe quel magasin — « tous les commerciaux peuvent traverser des magasins ». La notion « un magasin = un responsable » (posée le 06/08 au matin) était une invention de ma part, jamais demandée, et elle bloquait le remplissage de la semaine.
- 2026-08-06 — Conséquences : écran `/perimetres` et `lib/data/team.ts` supprimés ; `store_assignments` n'est plus lue ni écrite (table conservée, sa suppression imposerait une régénération des types) ; plus de liseré de couleur sur la liste des priorités, puisqu'aucun magasin n'appartient à personne. Les couleurs de personne restent sur le planning (une ligne par commercial) et les absences.
- 2026-08-06 — Nouvel algorithme de remplissage : un SEUL pool de magasins pour toute l'équipe, servi créneau par créneau dans l'ordre jour-par-jour (lundi pour tout le monde, puis mardi…). Les magasins les plus en attente partent donc en début de semaine, répartis entre les commerciaux, et un magasin servi disparaît du pool — personne ne peut le recevoir deux fois.
- 2026-08-06 — La lecture RLS du portail commercial ne dépendait heureusement plus du périmètre : `stores_read_tournee` (migration 00009) suffit à lire les magasins de sa tournée. Aucune migration nécessaire pour ce changement de modèle.
- 2026-08-06 — Défaut d'affichage corrigé : quand le chargement de la semaine échouait, l'écran affichait « Personne ne porte de visites » — un état vide déguisant une erreur, qui envoie chercher au mauvais endroit. L'erreur a désormais la priorité sur l'état vide.
- 2026-08-06 — `porte_visites` n'avait AUCUNE interface : si le drapeau était faux, l'écran renvoyait vers un réglage qui n'existait pas. Interrupteur « Fait des visites » ajouté dans l'écran Équipe.
